# FContex Admin 项目介绍

> 本文档按目标状态介绍 FContex Admin。其前身 fcontex 内容管理系统由 alan 于 2012 年开发并维护至 1.0.4（对外最后发布版本），此后转为自用。现整理散落在各项目中的修改合并为 1.0.5，转型后发布 1.1.0，并持续迭代至 1.1.9（在 src 目录下），更名为 FContex Admin。
>
> 文中未特别标注"现状"的内容，均为转型目标。

## 一、系统简介

项目官网：www.fcontex.com

FContex Admin 是一个纯 PHP 的轻量级管理后台开发框架，用于快速构建各类需要后台管理界面的系统：设备管理、业务后台、内部工具、小型信息系统等。项目以 MIT 协议开源发布，见根目录 LICENSE 文件。

一句话定位：

> 为 AI 开发而生，也为不一样的管理界面而生——纯 PHP、零构建链的模块化后台框架。

它面向这样的开发者：需要 FastAdmin、BuildAdmin 这类后台框架的能力，但不接受前后端分离的复杂度、Vite 等前端编译工具链，以及 TP 系权限节点体系的繁琐。FContex Admin 提供同样的开箱即用能力，但保持纯粹。

## 二、亮点

### 1. AI 开发（AI-first）

- 单语言、小体积、强约定：134 个 PHP 文件、16,723 行、0.55 MB，整个项目可装进一个 AI 上下文。
- 命名约定唯一：模块名 → `FCModuleXxx` 类名 → `fc.xxx` 动作模式 → `模块.实体.动词` 权限键，AI 可直接生成模块、补权限并自检。
- 无工具链编排负担：改完即生效，没有编译、打包、版本对齐环节。
- 配套规划：`AGENTS.md` 项目说明与模块脚手架，让 AI 按统一约定产出可运行模块。

### 2. 告别千篇一律，尝试不一样的管理界面

- 后台是窗口化的桌面系统（WebOS），而非千篇一律的"顶栏 + 侧栏 + 标签页"布局：窗口多开、开始菜单、任务栏，桌面即启动器。
- 模块图标随模块装卸自动增减，桌面状态即系统状态；窗口系统与业务部件（表单、表格、上传等通用控件）解耦，业务模块不感知窗口层。
- 双皮肤 default/dark：皮肤跟随用户，支持"用户自选 → 记忆 Cookie → 出厂基准 → 内核兜底"四级回落。
- 小屏幕自动退化为单窗口全屏，不另做一套移动端界面。

### 3. 零构建链

- 纯 PHP + 服务端渲染，单语言、零构建链，不依赖 Node、Vite、Composer 等外部工具。
- 部署即拷贝：上传目录、配好数据库即可运行，只需一个 MySQL 数据库。

### 4. 模块化 + 热拔插

- 每个功能是一个模块，通过后台"模块管理"界面安装、禁用、排序、卸载，无需改代码。
- 装模块如装 App：模块是唯一的一等扩展机制，拥有自己的数据表、权限、菜单和生命周期。
- 模块可直接使用内核提供的公共设施（脚本、组件、皮肤、鉴权），内核没有的自行提供（放在模块自己的 `scripts/`、`icons/` 中）。
- 最小安装只含内核（system + member），装什么长什么。

### 5. 声明式权限控制

- 模块在 `module.php` 中声明权限，安装时注册进内核，动词词表简洁（select / insert / update / delete / order 等），可自由扩展。
- 用户组持有权限集合，同一分组权限一致，精确可配置。
- 不做规则节点自动采集、不做多表关联映射：菜单显隐与动作入口共用同一套权限校验闭环，简洁且完整。

### 6. 响应式界面

- 界面适配移动端访问，后台管理不受设备限制。
- 桌面端保留 WebOS 窗口体验，小屏幕自动退化为单窗口全屏布局。
- 内容页随宽度降级：表单单列堆叠、工具栏换行，列表表格在容器内横向滚动并固定首列。

### 7. 轻量可通读

- 全部代码自包含、可通读，没有一行需要"相信框架"的黑盒。
- 出问题能直接定位到具体一行，不依赖生成代码与黑盒调试。

## 三、系统架构

### 总体结构

```
FContex Admin
├── 内核（不可拆卸）
│   ├── system    内核 + 后台桌面应用（路由/数据库/模板/配置/日志/缓存/附件/模块管理）
│   └── member    鉴权与用户组权限（登录/用户/分组/权限校验）
├── 可选模块（装卸自由）
│   ├── content   CMS 能力（栏目/文章/页面/标签/导航/主题）——从必装降级为可选
│   ├── message   评论与留言
│   └── ...       任意业务模块
└── store/        配置、缓存、上传等运行时存储
```

内核边界原则：内核不包含任何业务概念。CMS 的内容类型、前台主题等概念属于 content 模块，不属于启动层。

依赖单向原则：依赖只能指向更早、更基础、更必然存在的一方。内核不依赖任何业务模块；业务模块可以使用内核的公共设施；模块之间，后来者可以依赖先有者（如 message 为 content 的条目提供评论服务），反向禁止。

### 请求流程

```
HTTP 请求
  → index.php
  → module/startup.php            引导：常量、session、内核对象
  → cls.router                    解析 QUERY_STRING 得到 module/action
  → module/<模块>/index.php        页面入口（模板渲染输出）
  → module/<模块>/control/?mode=   动作接口（数据读写，统一权限校验）
```

开启 Rewrite 时将路径重写为 `index.php?<module>` 形式，路由从 `QUERY_STRING` 解析。

### 模块结构

```
module/<模块名>/
├── module.php     FCModule<Name> 声明类（类名 = FCModule + 首字母大写的目录名）
│     $basic       基本信息（名称/版本/作者/说明）
│     $rights      权限声明（安装时注册进内核）
│     $menus       后台菜单声明（引用 $rights 中的权限）
│     install()    安装回调（建表、初始化）
│     uninstall()  卸载回调（清理）
├── index.php      页面入口
├── control/       动作接口（?mode=...）
├── library/       模块类库
├── template/      模板
├── scripts/       模块私有静态资源（可选）
├── icons/         模块图标（桌面与菜单引用）
└── install.mysql.sql   建表脚本（安装时自动执行，可缺省）
```

### 内核全局对象

| 变量 | 类 | 职责 |
|------|----|------|
| `$A` | FCApplication | 应用核心，配置加载、类库加载、通用工具 |
| `$U` | Member | 当前用户、登录状态、权限判断 |
| `$D` | Database | 数据库访问层（PDO / MySQL 驱动） |
| `$T` | Template | 模板引擎（变量绑定、页面渲染） |
| `$R` | Router | 路由解析与分发 |

（内容对象 `$C` 属于 content 模块：使用方通过 `FCApplication::loadLibrary('content')` 获取，用于前台主题渲染（`$C->display()`）与内容数据访问；内核不含任何业务对象。）

### 权限模型

```
模块 $rights 声明权限 ──安装──▶ 内核权限注册表
                                    │
用户组 ◀──持有──────────────────────┤
                                    │
菜单显隐 ◀──引用────────────────────┤
动作入口 ◀──校验────────────────────┘
```

- 权限在模块安装时声明式注册，卸载时随模块移除。
- 后台菜单与动作入口共用同一权限来源，菜单引用的权限必须存在于模块声明中（安装时校验）。
- 每个动作入口有统一权限检查点，不依赖菜单隐藏兜底。

## 四、与主流后台框架对比

| | FContex Admin | FastAdmin | BuildAdmin |
|------|------|------|------|
| 语言/框架 | 纯 PHP 自研内核 | ThinkPHP | ThinkPHP |
| 前端形态 | 服务端渲染 + 窗口桌面 | jQuery + Bootstrap | Vue3 + TypeScript |
| 构建链 | 无 | 无（RequireJS） | Vite / Node |
| 权限 | 模块声明式，动词词表 | 规则节点 + 三表关联 | 规则节点 + 三表关联 |
| 后台界面 | WebOS 窗口化 | 传统布局 | 传统布局 |
| 扩展机制 | 模块热拔插 | 插件 + 插件市场 | 插件 |
| 数据库 | MySQL | MySQL | MySQL |

差异化的本质：别的框架在"更多能力"的方向上加码，FContex Admin 在"更少负担"的方向上做到底。

运行环境：PHP 7.3 及以上（推荐 8.x）、MySQL 5.5.3+（推荐 5.7 / 8.0）；无 Composer、无 Node。

## 五、安全性

安全边界全部在服务端：前端的校验、隐藏与提示只影响体验，不承担防护职责。以下机制均已落地并逐项验证。

### 1. 密码存储

- 统一用 `password_hash()`（bcrypt，PHP 5.5+）存储，自带随机盐与自适应成本，库中既无明文也无任何可逆编码。
- 登录用 `password_verify()` 校验；算法成本升级后，用户下次登录成功时自动 `password_needs_rehash()` 重算。
- 新增用户、编辑用户、重置密码、安装向导写入，全部走同一个 `password` 类库封装。
- 前端仍提交 md5 值，仅用于避免明文出现在请求中，不再承担任何凭据作用。

### 2. 会话与 Cookie

| 措施 | 说明 |
|------|------|
| `HttpOnly` | 会话与登录 Cookie 禁止 JS 读取，降低 XSS 窃取风险 |
| `SameSite=Lax` | 跨站请求不携带会话 Cookie（PHP 7.3+ 生效，低版本由浏览器默认策略兜底） |
| `Secure` | HTTPS（443）下自动标记 |
| 会话重建 | 登录成功后 `session_regenerate_id(true)`，防会话固定攻击 |

"记住登录"不存用户名、不存可逆凭据：服务端生成 32 字节随机令牌，数据库只存其 sha256 摘要，有效期 7 天；退出登录立即清空，旧令牌随即失效。

### 3. CSRF 防护

- 会话级随机令牌同时写入可读 Cookie `csrf_token`，前端 `$$.post` / `$$.get` 统一在 `X-CSRF-Token` 请求头回传。
- `startup.php` 对 `mode=fc.*` 的 Ajax 请求统一比对令牌，不通过直接返回 `ERR|会话校验失败`，不进入业务代码。
- 登录、找回密码、验证码等匿名接口入白名单；页面导航类请求（`<a href>`）不参与校验，避免误伤。
- 跨站页面无法读取令牌，也无法为普通表单添加自定义请求头，因此写操作无法被伪造。

### 4. 权限校验

- 每个动作入口的第一条语句就是 `checkRights('模块.实体.动词')`，菜单显隐只是体验优化，安全边界在动作入口。
- 权限在模块安装时声明式注册、卸载时随模块移除；安装时校验菜单引用的权限必须存在于本模块声明，防止拼写错误与跨模块误引。

### 5. SQL 注入

- 读写统一走 PDO 预编译 + `?` 参数绑定，驱动的 `run()` 是唯一执行出口，业务代码不拼接 SQL 值。
- 仅 `in (1,2,3)` 这类无法参数化的片段允许字符串拼接，且必须先经 `intval` 或 `^[0-9]+(,[0-9]+)*$` 正则校验。

### 6. 登录防护与配置

- 登录失败限流：IP 与账号双维度计数（账号不区分大小写），统计窗口内失败达到 `loginAttempts`（默认 5）次即锁定 `loginLock`（默认 15）分钟，提示剩余次数与解锁时间；阈值在 `store/config/system.settings.php`，无需改代码。
- 计数文件落在 `store/cache/login/`，`flock(LOCK_EX)` 原子读改写，并发请求无法多试；文件带 `<?php exit; ?>` 头，直接访问不输出内容。
- 取客户端 IP 只信 `REMOTE_ADDR`，`HTTP_CLIENT_IP` / `HTTP_X_FORWARDED_FOR` 默认忽略（可被伪造）；站点位于 CDN 或反向代理之后时，需在配置里开 `trustProxy` 并填写 `trustProxyList` 白名单。IPv4 与 IPv6 均正常参与计数。
- 数据库配置 `store/config/system.database.php` 不入版本库，仓库只提供 `system.database.sample.php`；由安装向导生成。
- 缺少数据库配置时自动跳转安装向导，不暴露部署细节。

### 7. 已知边界

- 动作接口的 `mode` 仍走查询串（决定分发），`args` 与表单数据一律走 POST（system / member / message / content 四个模块已完成）。
- 权限只到操作级，不做数据行级权限——这是有意的设计边界，复杂的数据范围控制由模块自行实现。
- 登录失败限流是单机文件计数：多机/多活部署时各节点独立计数，需要全局限流时请在外层（Nginx `limit_req`、网关或 WAF）再补一层。

## 六、适用场景

- **中小型自用系统与内部工具**：设备台账、业务后台、信息登记、内容站点等，以表单、列表、权限为主的管理场景。
- **追求快速交付的个人与外包项目**：整份代码拷进 Web 目录、配好数据库即可上线，没有构建、打包、版本对齐环节。
- **希望完全掌控源码的团队**：全部代码自包含、可通读，没有需要"相信框架"的黑盒，出问题能直接定位到具体一行。
- **功能会持续生长、但不想背框架负担的项目**：功能按模块装卸，最小安装只含内核，装什么长什么，扩展不必改内核。
- **需要统一桌面与移动端体验的后台**：桌面端保留 WebOS 窗口化体验，小屏幕自动退化为单窗口全屏，不另做一套移动端界面。
- **需要为自有前端提供后台与接口的项目**：小程序、H5、App 的后台管理与数据接口可由模块的页面入口与动作入口承担，不引入新的服务端技术栈。
- **AI agent 参与维护的长期项目**：单语言、小体积、强约定，agent 可在单一上下文内理解整份项目并安全修改。

### 不适合谁

- 需要复杂工作流引擎、报表引擎、低代码可视化设计器的项目：FContex 不提供这些重型设施。
- 要求前后端分离、多端技术栈矩阵（Java/Go/多端 App 同步）的团队：这是有意回避的方向。
- 需要数据行级权限、多租户等复杂权限模型的项目：内核只做到操作级，需模块自行实现。
- 希望靠插件市场即装即用大量现成业务功能的用户：当前生态以自研模块为主。

## 七、现状与路线

现状（1.1.9，src 目录）：CMS 全功能可用，模块机制、模块管理、窗口化后台均已成熟运行多年。

转型路线，按优先级：

1. ✅ 内核解耦：startup 引导层瘦身，业务对象与业务常量移出内核（system 对 content 零依赖）。
2. ✅ 最小安装验证：仅 system + member + 业务模块可完整运行，content 可禁用。
3. ✅ 默认路由改为后台桌面：默认模块可配置，未设置时回退 system 控制台。
4. ✅ 更换失效组件：上传控件已改为 FormData/XHR（脱离 Flash），富文本编辑器由 KindEditor 换为自托管的 Quill 2（含 HTML 源码视图）。
5. ✅ 权限校验闭环：动作入口检查已统一，安装模块时校验菜单引用的权限是否在本模块声明中。
6. ✅ 插件体系退役：模块成为唯一扩展机制，旧插件体系已整体移除。
7. ✅ 数据库 API 收敛：统一 PDO 与参数绑定，读取门面 `DB::table()` + 查询构造器，写方法与事务闭包化。
8. ✅ 双层模块菜单：菜单支持"分组 + 叶子"两层结构，单组模块视觉与旧扁平菜单一致，复杂模块可挂多个分组。
9. ✅ 皮肤体系：用户级皮肤 + 四级回落 + 公共记忆 Cookie，登录页可记住上次皮肤。
10. ✅ 上传下载改造：附件 token 化不可枚举，下载支持单段断点续传与流式输出，删除文件后自底向上清理空目录。
11. ✅ 配置归属拆分：手工配置（system.settings）与自动化配置（system.site / system.modules）分离。

待办：

1. ✅ 模块脚手架与 `AGENTS.md`：`bin/newmodule.php` 生成模块骨架，固化 AI 生成模块的统一约定。
2. ✅ GitHub 开源发布：仓库已公开，tag `v1.1.9` 与 Release 包可下载，公开仓库只放 MIT 部分；Gitee 镜像仍待建。
3. ✅ 官网上线：`fcontex.com` 已上线，含 `llms.txt`、`sitemap.xml`、分享卡与搜索引擎规则；首屏与文档入口均指向仓库。
